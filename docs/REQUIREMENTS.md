# 需求文档

## 1. 文档说明

本文档基于当前代码实现反向整理，不代表原始立项文档。目标是把系统已经承载的业务需求、规则和边界明确化，便于继续开发、评审和测试。

## 2. 业务背景

系统用于服装车缝产线的工位排产。业务上需要把某个款式的具体工序，与企业内部的标准工序能力库对应起来，再结合员工技能和效率，生成可执行的工位分配结果和布局视图。

## 3. 用户角色

### 3.1 产线管理人员

职责：

- 导入工时表和技能矩阵
- 审核 AI 给出的工序映射
- 维护员工技能
- 运行排产并查看结果
- 调整工位布局
- 导出报表

### 3.2 工艺/IE 人员

职责：

- 维护标准工序命名
- 处理新增工序建议
- 校验工序顺序、效率、平衡率和搬运距离

## 4. 业务目标

- 统一款式工序与标准工序口径
- 减少人工逐条映射成本
- 基于员工技能与效率生成可执行排产
- 支持排产后工位布局优化
- 输出可追溯的结果与审核记录

## 5. 功能需求

## 5.1 导入工时表

系统应支持导入 Excel 或 CSV 格式的标准工时表。

工时表至少应包含以下字段：

- 款式编号
- 部件
- 工序号
- 工序描述
- 标准时间
- 标准单价

系统应：

- 校验缺失必填列
- 校验同一款式下工序号是否重复
- 校验标准时间是否为正数
- 对非法标准单价给出告警并按 0 处理
- 为每条工序生成稳定主标识与版本标识
- 推导工序前后依赖关系

## 5.2 导入员工技能矩阵

系统应支持导入 UTF-8 CSV 格式的员工技能矩阵。

姓名列应兼容以下列名之一：

- 姓名
- 员工
- 员工姓名
- 名称

系统应：

- 识别员工基本信息
- 将技能列转换为标准工序库
- 解析效率值，兼容：
  - `0.8`
  - `80%`
  - `80`
- 跳过空白效率
- 对非法效率给出告警
- 对重复员工给出错误

## 5.3 工序映射

系统应支持将款式工序映射到标准工序。

映射过程应包含以下优先级：

1. 已存在的当前款式映射
2. 历史知识库命中
3. LLM 自动映射
4. 本地相似度回退

系统应为每条映射记录提供：

- 原工序描述
- LLM 候选标准工序
- 最终标准工序
- 最终标准工序 ID
- 置信度
- 原因
- 是否建议新增标准工序
- 是否已人工确认

## 5.4 人工确认映射

系统应允许用户对低置信度或建议新增的映射进行人工确认。

用户应可以：

- 选择现有标准工序
- 直接输入新的标准工序名称
- 保存最终确认结果

当用户输入新的标准工序名称时，系统应：

- 自动创建新的标准工序
- 将该映射标记为已人工确认
- 提示用户回到技能矩阵页补充员工掌握情况

## 5.5 技能矩阵维护

系统应支持员工技能的增删改。

用户应可以：

- 为指定员工新增某项标准工序技能
- 修改技能效率
- 删除技能

系统还应支持查看“待补员工技能的标准工序”，即当前没有任何员工掌握的标准工序。

系统当前还支持：

- 将“待补员工技能的标准工序”拖拽到某个员工姓名上
- 弹出效率输入框
- 直接完成新增或更新技能

## 5.6 排产前校验

系统在执行排产前应至少校验：

- 已选择款式
- 款式已有工序数据
- 款式工序已全部完成映射
- 映射已人工确认完成
- 参与排产的员工已选择
- 最终标准工序均至少有一名已选员工掌握

不满足条件时，系统应阻止排产并给出明确提示。

## 5.7 排产计算

系统应根据：

- 款式工序
- 工序依赖关系
- 员工技能
- 员工效率

生成工位分配结果。

当前实现的业务规则包括：

- 每名被选员工都必须被分配到工位
- 每道工序只能分配给一个工位
- 工序必须满足前驱工位顺序约束
- 若员工未掌握某工序，则仍可参与求解，但按默认低效率处理并给出警告

系统应输出：

- 工位数
- 每个工位对应员工
- 每个工位承接的工序
- 工位负荷
- 平衡率
- 节拍
- 总有效工时

## 5.8 工位布局与搬运距离

系统应支持在排产结果基础上生成工位布局。

系统应：

- 提供默认直线布局
- 计算工位之间的总曼哈顿搬运距离
- 支持用户拖拽工位位置
- 在拖拽后实时更新搬运距离

## 5.9 报表导出

系统应支持导出：

- Excel 报表
- PDF 报表

导出内容应至少包含：

- 排产结果
- 映射确认摘要
- 导入异常
- 核心指标

## 6. 非功能需求

## 6.1 可用性

- 作为桌面工具运行，不依赖服务端即可完成主流程。
- 即使未配置 DeepSeek API Key，也应允许通过本地回退完成演示和人工确认。

## 6.2 性能

- 中小规模问题应尽量使用精确求解。
- 当问题规模较大或求解器超时，应自动回退到较快的贪心算法。
- UI 长耗时操作应通过后台线程执行，避免界面卡死。

## 6.3 可追溯性

- 导入结果、映射结果、人工确认结果、布局结果应可持久化。
- 同一描述的历史人工确认结果应可复用。

## 6.4 可维护性

- 领域对象应统一在 `data/models.py` 中定义。
- 核心业务逻辑应尽量位于 `core/`，UI 负责交互与展示。
- 数据库启动时应支持自动建表和轻量迁移。

## 7. 业务规则

- 标准工序库是排产与技能维护的统一口径。
- 款式工序不是直接用于员工技能匹配，必须先映射到标准工序。
- 建议新增标准工序的映射不能直接视为已完成确认。
- 一个标准工序如果没有任何员工掌握，系统不允许进入正式排产。
- 当前规则不允许“已选员工闲置”。

## 8. 输入输出定义

### 8.1 输入

- 工时表文件
- 技能矩阵文件
- 映射人工确认结果
- 参与排产的员工选择
- 工位拖拽坐标调整

### 8.2 输出

- 映射结果
- 员工技能维护结果
- 排产结果
- 平衡率、节拍、总距离等指标
- Excel/PDF 报表

## 9. 边界与暂不支持

基于当前实现，以下能力暂不支持或未显式实现：

- 一个工序拆分给多名员工协同完成
- 允许部分已选员工空闲
- 多产线/多车间联合求解
- 工位设备、场地容量、班次等高级约束
- 基于 MES 或 ERP 的在线实时同步

## 10. 验收建议

建议以以下场景作为验收主线：

1. 导入一份合法工时表与技能矩阵，确认能正常生成员工与标准工序库。
2. 对低置信度映射进行人工确认，确认保存后能进入排产。
3. 对新增标准工序补录员工技能，确认“未覆盖标准工序”数量下降。
4. 执行排产，确认结果中每名已选员工均有工位。
5. 拖拽工位后，确认总搬运距离实时变化。
6. 导出 Excel/PDF，确认关键结果与界面一致。
